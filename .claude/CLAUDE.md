# Working in knowledge-base

A file-based agent memory store: markdown files with YAML frontmatter, one
folder per memory type, plus a stdlib-only CLI. No database, no vector store,
no runtime dependencies.

**`memory/AGENT.md` is the authoritative contract.** Read it before doing
anything here — it carries the type taxonomy, the confidence rubric, the
`authority` field, and the restatement check that this file only summarises.

## Layout

- `memory/<type>/` — the entries. Seven types: `semantic`, `episodic`,
  `procedural`, `working`, `retrieval`, `parametric`, `prospective`.
- `memory/AGENT.md` — the contract above.
- `scripts/kb.py` — the CLI: everything below is a subcommand of it.
- `scripts/build_site.py` — builds the published site into `site/` (gitignored).
- `scripts/serve.py` — local editor; same helpers as the CLI, same log.
- `scripts/mcp_server.py` — the store over MCP (stdio); writes are staged in
  the working tree, never committed.
- `.kb/` — `schema/`, `templates/entry.template.md`, `log.md`, `verdicts.json`,
  `golden.json`.
- `tests/` — `python3 -m unittest discover -s tests -q` (takes ~2.5 min).
- `.github/workflows/` — `kb-lint.yml` (push + weekly strict), `kb-due.yml`
  (daily), `pages.yml`.

## Adding a memory

1. `scripts/kb.py capture --check --text "<the claim, in your words>"` first.
   It names the entries that already hold that claim; extend one rather than
   filing a near-twin. `kb.py capture --extend <name>` does that.
2. Otherwise `scripts/kb.py new --type <type> "<name>"` scaffolds from the
   shared template, then fill in the body and set `confidence` honestly.
3. Link related entries with `scripts/kb.py link` — never by hand-editing the
   `links:` list, and never with `kb.py set links`.

## Before committing

- `python3 scripts/kb.py lint` (add `--strict` to see what the weekly cron
  gates on) and `python3 scripts/kb.py triage`.
- `python3 -m unittest discover -s tests -q` for any change under `scripts/`.
- `scripts/kb.py verify <name> --note "<what you checked>"` when you have
  actually re-checked a claim. The date alone cannot say whether anyone
  looked, so a verify without a note is a schedule change, not a review.

## Never

- Hand-edit `site/` — it is generated by `build_site.py` and gitignored.
- Change an entry's `name` or `type` in place; both define its file location.
- Lower the `dupes` threshold to "catch more" — that is a different command
  from `candidates`, and its regression test will fail.

`ROADMAP.md` records what has been built and, for each thing deliberately not
built, the condition that would revive it. `AUTONOMY.md` governs scheduled
autonomous sessions; `DEBRIEF.md` is their shared record.
